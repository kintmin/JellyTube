# docs — 사용자 관점의 기능 문서

**코드를 읽어도 알 수 없는 것만 담는다.** 무엇이 어떻게 동작하는지는 코드가, 어떤 순서로
그렇게 됐는지는 PR 이 갖는다. 여기 남는 것은 **왜 그렇게 정했는지**와 **의도적으로 하지
않은 것**이다.

한 것은 코드에 있다. **안 한 것만 어디에도 없다.** 그 자리가 여기다.

## 적는다 / 적지 않는다

| 적는다 | 적지 않는다 |
|---|---|
| 사용자에게 하는 약속 | 화면에 무엇이 보이고 어떤 순서로 동작하는지 |
| **의도된 제약** — "이렇게 안 되는 게 맞다" 와 이유 | 클래스명·파일명·패키지 경로 |
| 다른 기능과 교차할 때 지켜야 하는 규칙 | 결정 이력·고려한 대안·진행률 (PR 몫) |
| 배치·문구·순서를 그렇게 고른 이유 | 이미지와 ASCII 레이아웃 |
| | `AGENTS.md` 가 이미 가진 제약 |

가늠자: **기능을 고쳤는데 여기 문장이 틀렸다면, 그 문장은 처음부터 여기 있을 게 아니었다.**
고치지 말고 지운다.

## 자리

| 자리 | 담당 |
|---|---|
| `DECISIONS.md` | 되돌리기 어렵고 여러 기능에 퍼지는 결정 |
| `ui-rationale.md` | 화면을 가로지르는 배치·제스처·파괴적 동작 원칙 |
| `features/<기능>.md` | 지금 있는 기능 하나 |
| `experiments/<기능>.md` | 지금 없는 기능 하나 |

- **파일 이름은 사용자가 그 기능을 부르는 이름이다** — 화면 이름도 패키지 이름도 아니다.
  내용은 한국어로 쓰고 파일 이름만 영어 kebab-case 로 적는다(`secret-mode.md`).
- 목록은 두지 않는다. 폴더를 열어 같은 것이 이미 있는지 먼저 본다.
- 반영되면 `experiments/` 의 파일을 지우고 내용을 `features/` 로 옮긴다. 두 자리에 같은
  기능을 동시에 두지 않는다.

## 넣을지 말지

**두 체를 다 통과하면 넣는다.**

1. **코드가 "왜" 를 말하지 않는가?** 재생을 OS 엔진에 맡기는 것처럼 자명하면 뺀다.
2. **그 "왜" 를 모르면 잘못 뒤집을 만한가?** 아무도 "이거 왜 이렇지" 라고 묻지 않는 것
   (이미지 로더, 네트워크 라이브러리)은 뺀다.

**둘째 체가 이 문서의 목적이다.** `DECISIONS.md` 는 설명이 아니라 **방어막**이다 — 사람이든
AI 든 "이거 이상한데 바꾸자" 고 할 때 근거를 내놓는 자리다. 그 말이 나올 만한 것만 들어간다.
영향 범위는 수록 여부가 아니라 **자리**를 가른다: 한 기능 안에서 끝나면 `features/`,
여러 기능에 걸치면 `DECISIONS.md`.

**결정이 바뀌면 고친다. 그건 어긋남이 아니라 정상이다.** 위험한 어긋남은 기능 변경마다
틀어지는 문장이고, 결정 변경은 몇 년에 몇 번이며 그때는 반드시 문서를 손댈 때다.

## 뼈대

```markdown
# <기능>                      ← features/

<사용자에게 하는 약속. 1~3줄>

## 의도된 제약
- <이렇게 안 되는 게 맞다> — <이유>

## 교차 규칙
- <다른 기능과 만날 때 지켜야 하는 것>

## 열린 질문
- <아직 정하지 않은 것>
```

```markdown
# <기능>                      ← experiments/

상태: 아이디어 | 해봤고 접음 | 보류
다시 보는 조건: <무엇이 바뀌면 다시 보는가>   (없으면 "닫힘")

## 무엇을 하려 했나
## 왜 지금 없나               ← 이 문서의 핵심
## 어디서 막혔나              ← 해봤을 때만. 안 해봤으면 지운다
```

**"보류" 에는 다시 보는 조건을 반드시 적는다.** 조건 없는 "나중에" 는 다시 보지 않는다.
쓸 수 없으면 "닫힘" 이다.

## 어긋남

기능을 바꾸는 작업은 **문서를 먼저 고치고 코드를 고친다.** 그 순서는 급할 때 건너뛰게 되므로,
실제로 잡는 것은 PR 전에 도는 `doc-drift-check` 다.

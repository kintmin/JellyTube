# 결정과 그 이유

되돌리기 어렵고 여러 기능에 퍼지는 결정만 담는다. 한 기능 안에서 끝나는 것은 `features/` 로 간다.

무엇을 골랐는지는 코드가 말한다. **당시 제약이 이 문서의 전부다** — 그게 없으면 몇 년 뒤에
"지금도 유효한가" 를 판단할 수 없다. 사정이 바뀐 항목에는 **지금은** 을 붙인다. 다시 볼
거리라는 표시다.

---

## 1. Kotlin Multiplatform + Compose Multiplatform

Kotlin 코어 하나를 Android·iOS·Desktop 이 공유하고, 화면도 CMP 로 공유한다.

- Android 토이 프로젝트로 시작해 Android 만 볼 생각이었다.
- iOS 포팅과 Swift 학습을 겸해 **KMP + TCA** 를 택했다. 도메인만 공유하고 화면은 OS 별로
  따로 만드는 PoC 를 한 화면으로 성공시켰다.
- Flutter·React Native 는 후보가 아니었다 — 이미 Android 코드가 있었다. iOS 네이티브도
  아니었다 — 도메인 로직을 그대로 쓰고 싶었다.
- Android 기능이 늘면서 화면을 둘로 유지하는 비용을 감당할 수 없어 **iOS 구조를 파기했다.**
- CMP 는 그 타협이다. **OS 친화적인 UI 를 포기하고 개발 속도를 얻었다.**

## 2. 완전 무료 — 서버를 두지 않는다

음원 추출·가사 번역·기기 간 전송이 모두 기기에서 끝난다. 앱이 호출하는 자체 서버가 없다.

- 이 앱은 **완전 무료**를 지향한다. 지속적으로 비용과 운영이 드는 서버는 후보가 아니다.
- 온디바이스 음악 앱에서 통신이 없는 것은 그 자체로 이점이다 — 반응이 빠르고 가볍다.
- 가사 번역에 LLM 을 쓰지 않는 것도 같은 이유다. **품질 저하를 감수한 선택이다.**

## 3. yt-dlp 를 Python 런타임째 번들한다

Android 는 Chaquopy, iOS 는 Python-Apple-support 로 Python 3.11 을 앱에 넣는다. 추출
스크립트는 `shared/data/src/python` 한 벌을 양쪽이 쓴다.

- 처음엔 다운로드를 직접 구현하려 했다. m3u8 처리가 까다롭고, 쓰려던
  [mobile-ffmpeg](https://github.com/tanersener/mobile-ffmpeg) 가 유지보수를 멈춰 파기했다.
- 유튜브가 추출 경로를 수시로 바꿔 직접 따라가기 어려웠다.
- 당시 Android 쪽에 제대로 유지보수되는 다운로드 구현이 없었다.
- PoC 를 여러 번 실패한 끝에, 이 분야에서 **업데이트가 가장 잦고 활발한** yt-dlp 를 골랐다.
  Python 기반이라 Android 포팅 방법을 찾다 가장 보편적인 Chaquopy 에 닿았다.
- 백그라운드 worker 에서 다운로드까지 확인하고 PoC 를 끝냈다.

**지금은** 당시 제약 셋이 다 풀렸다. FFmpeg 는
[ffmpeg-kit-next](https://github.com/arthenica/ffmpeg-kit-next) 로 이어졌고,
[NewPipeExtractor](https://github.com/TeamNewPipe/NewPipeExtractor) 같은 대안이 생겼고,
유명 레포의 해결 방법을 AI 로 Kotlin·웹뷰에 옮기는 길도 열렸다. 다시 보려면 Python 번들의
비용(앱 용량, iOS Vendor 준비 단계, yt-dlp 를 주기적으로 갱신해야 하는 유지보수)과 대조한다.

## 4. 앱 스토어에 배포하지 않는다

GitHub Releases 로 APK 를, SideStore 소스로 IPA 를 준다. 무료 Apple ID 로 서명하므로
사용자가 7일마다 갱신한다.

- **3번의 귀결이다.** 유튜브 다운로드는 양 스토어 정책에 걸려 반려될 가능성이 높다.
- 위험 앱으로 분류돼 제재받는 쪽이 더 위험해서 올려 보지도 않았다.
- 7일 갱신·메일 공지·앱 안의 업데이트 알림이 모두 여기서 나왔다.

**아직 확인하지 않은 것**: 아이콘과 제목만 바꾸면 되는지. 정책상 양쪽 다 안 될 가능성이 높다.

## 5. 파일 공유는 폰이 서버다

폰이 Ktor 서버를 포그라운드 서비스로 띄우고 데스크톱이 올려 보낸다. 데스크톱은 jmdns(NSD)로
폰을 찾는다.

- 취미 플레이리스트를 남에게 공유하거나 기기를 바꿀 때 그대로 옮기는 것이 이 앱의 이점이다.
- 그것을 OS·플랫폼에 구속되지 않고 하려면 받는 쪽이 서버여야 했다. NSD 로 서로 찾게 해서
  주소를 입력하지 않아도 되게 만들었다.

## 6. 로컬 DB 는 Room + 번들 SQLite

Room 을 KMP 로 쓰고, Android·iOS 빌더가 모두 `BundledSQLiteDriver` 를 꽂는다.

- Android 로 시작한 프로젝트라 Room 이었고, 하위 호환 때문에 바꿀 수 없었다. SQLDelight 는
  고려하지 않았다.
- 번들 SQLite 는 **iOS 때문에 필수다** — Room KMP 의 비Android 타겟에는 쓸 드라이버가 없어
  직접 줘야 한다. Room 이 끌고 오는 것이 아니라 `shared/data` 가 선언한다.
- Android 도 같은 드라이버를 쓰는 것은 선택이다. 로직이 간편해지지는 않는다. 효과는 양
  플랫폼이 **같은 SQL 엔진**을 쓰는 것 — 한쪽에서 통과한 쿼리가 다른 쪽에서 달라지지 않고,
  구형 기기의 낡은 SQLite 문법 제약에 막히지 않는다.

## 7. DI 는 Koin

Koin 으로 런타임에 조립한다.

- Hilt 를 쓰다 옮겼다. KMP 에서 Hilt 가 안 된다.
- 컴파일 타임 검증을 포기한 대가가 따라온다 — UseCase 가 170개를 넘는 지금은 빠진 바인딩이
  빌드가 아니라 실행 중에 드러난다.

## 8. 로그와 오류 수집은 Sentry

Sentry KMP SDK 를 쓴다. 갈아타기 쉽게 `shared/log` 가 API 만 갖고 구현은 `shared:data` 에 둔다.

수집 목적은 둘이다.

- **크래시 확인.**
- **사용자 패턴 확인** — 어느 기능을 자주 쓰고 어느 기능이 소홀한가, 주로 어떤 곡을 듣는가.
  취향 패턴과 곡 추천으로 발전할 토대다.

- Firebase Crashlytics + GA4 로 시작했다. 실시간 수집이 어렵고 오류·로그·기기 정보가 흩어져
  Sentry 로 옮겼다. 언제든 다시 바뀔 수 있다.
- **비밀모드에서 듣는 곡과 플레이리스트는 수집하지 않는다.** 집계할 이유가 없는 개인적인
  것이고, 취향 패턴에 섞이면 오히려 혼선이다.

**무엇을 패턴으로 수집할지 고르는 기준은 아직 없다.** 크래시 쪽은 분명하지만 패턴 쪽은 "나중에
쓸모 있을 것 같은 것" 을 그때그때 담아 왔다. 어느 로그를 쓰는 방법은 `shared/log` 의 규약이
정하고 있으니, 남은 것은 **무엇을 모을 값이 있는지**다. 기준이 없으면 모으는 양만 늘고 해석은
안 된다.

## 9. OS 가 하는 백업에 기대지 않는다

클라우드 자동 백업에는 아무것도 싣지 않는다. 되돌리는 책임은 앱 안의 백업과 기기 간 이전이 진다.

- 클라우드 자동 백업은 **주기를 정할 수 없고 됐는지 안 됐는지 확인할 길이 없다.** 거기에 복구를
  걸면 사용자에게 약속할 수 없는 것을 약속하게 된다.
- 처음에는 앱 안에 백업 사본을 두고 **그것만** 클라우드에 실었다. 재설치하면 그 사본이 돌아와
  앱이 스스로 되돌릴 백업을 찾을 수 있었다. 그러나 그 길은 Android 에서만 되고, 사본 하나 때문에
  **용량 한도와 "두 사본 중 어느 것이 최신인가" 가 따라왔다.**
- Android 는 클라우드와 기기 간 이전을 가를 수 있어 **기기 이전만 남겼다.** 되면 공짜로 좋은
  것이고, 안 돼도 복구 경로가 바뀌지 않는다.
- iOS 에는 그 둘을 가르는 API 가 없다. 하나를 빼면 함께 빠지므로 통째로 빼면서 **앱 데이터를
  iCloud 로 흘리지 않는 쪽**을 골랐다.
- 대가: 백업이 음원을 싣지 않으므로 **직접 올린 음원과 편집본은 기기를 잃으면 사라진다.**
  Android 는 이미 그 상태였고 iOS 가 거기에 맞춰졌다. 기기를 바꿀 때는 기기 간 이전으로 옮긴다.

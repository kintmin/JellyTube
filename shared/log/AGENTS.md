## Module: shared:log

**Role**: 로깅 API 와 그 모델만 정의한다. 구현은 하나도 없다.

---

## 이 모듈은 API 전용이다

로깅 인터페이스와 모델을 선언하고, 실제로 어디에 쓰는지는 모른다 — 수집기도, 콘솔도,
파일도 여기 없다.

**구현은 `shared:data` 의 `commonMain` 한 벌이다.** 수집기 SDK 가 두 플랫폼에서 같은 Kotlin API
를 주므로, 플랫폼마다 구현을 두면 같은 이벤트가 기기별로 다르게 쌓일 길만 생긴다.

## 여기 두지 않는 것

- 수집기 SDK 의존과 실제 로그 출력 → `shared:data` 의 구현
- 구현의 DI 배선 → `shared:data` 의 DI

---

## 실패는 오류 로그로 보낸다

디버그 로그는 Issue 가 되지 않아 스택도, 묶기도, 알림도 없다. 실패는 오류 로그로 보내고 예외가
있으면 넘긴다 — 메시지에 문자열로 붙이면 스택이 사라진다.

**같은 실패를 두 번 올리지 않는다.** 아래 계층이 이미 실패로 보냈으면(예외를 든 이벤트 포함)
위 계층은 디버그 로그로 맥락만 남긴다. 둘 다 올리면 한 번의 실패가 Issue 두 개가 된다.

**실패를 빈 값으로 바꾸기 전에 남긴다.** `getOrNull`·`getOrDefault` 로 흡수하면 화면에는 "없음"으로만
보이고 원인은 어디에도 남지 않는다.

**상태를 바꾸는 사용자 동작은 그 유스케이스에서 디버그 로그로 남긴다.** 앱 로그는 사용자 히스토리라,
무엇을 했는지 그것만 보고 재구성할 수 있어야 한다. 무엇이 바뀌었는지 알 수 있게 대상 id 를 싣는다.

---

## 비밀 데이터는 찍는 쪽이 데이터로 판정해 가린다

로그 구현은 비밀모드를 보지 않는다. 비밀모드는 화면 세션이라 백업 복원·백그라운드 작업처럼
비밀 데이터를 다루는 동안 꺼져 있을 수 있다. 곡·플레이리스트의 이름과 주소는 그 데이터가
비밀인지를 호출자가 넘겨 가리고, 판정할 수 없으면 가린다. 가리는 API 의 판정 인자에 기본값이
없어 빠뜨리면 컴파일되지 않는다.

## 모델 이름에 수집기 이름이 들어가는 것 — 인정된 예외

`android/app/AGENTS.md` 의 **"port 이름에 플랫폼 기구를 넣지 않는다"** 와 어긋나 보이지만
**의도한 예외다.**

- **수집기 선택이 제품 결정과 엮여 있다.** 어떤 이벤트를 분석 도구로 보내고 어떤 것을 크래시
  리포터로 보낼지는 플랫폼 사정이 아니다. 수집기별로 보낼 것이 갈리면 그때 모델도 갈리는 것이
  맞고, 그러면 이름이 수집기를 가리켜야 읽힌다.
- **묶으면 제약을 둘 자리가 사라진다.** 수집기마다 이름 길이·파라미터 수·예약어가 달라서,
  하나로 추상화하면 그 차이를 어디에 적을지가 없어진다.
- 그 규칙은 **같은 일을 하는 기구가 플랫폼마다 다른** 경우를 위한 것이다(백그라운드 작업,
  재생 엔진). 수집기는 반대로 **두 플랫폼이 같은 것**을 쓴다.

OS 기능은 여전히 그 규칙을 따른다. 이 예외는 수집기에만 적용된다.
